# CBL-3.3. Устойчивость: таймауты, ретраи с backoff, circuit breaker, bulkhead

| Поле | Значение |
| :-- | :-- |
| Эпик | E3, Connector |
| Репозиторий | `cbl-connector` |
| Размер | M |
| Волна и параллельная группа | W1-CONNECTOR |
| Зависит от | 3.1 |
| Версия контрактов | `cbl-protos@cf-1` (не меняется) |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

Внешний шлюз - единственный неконтролируемый участок денежного контура (`CBL-000`,
T-01): Payment вызывает Connector с дедлайном 5 с, Connector - провайдера. Задача 3.3
оборачивает порт `domain.PaymentGateway` декоратором устойчивости: пер-попыточные
таймауты, ретраи только безопасных вызовов с экспоненциальным backoff и jitter,
circuit breaker на провайдера и bulkhead ограничения параллелизма. Реальный адаптер
провайдера (3.2) остается за KI-01; декоратор подключается роутером 3.4.

## 2. Границы

In scope: пакет `internal/gateway` с декоратором `Resilient` (реализует
`domain.PaymentGateway`), классификация ошибок провайдера (временная/постоянная),
конфигурация из env, unit-тесты с детерминированным временем.
Out of scope: адаптеры провайдера и HTTP-клиент (3.2), роутер и Redis-конфигурация (3.4),
контрактные тесты адаптеров (3.7), метрики Prometheus (0.7), общий Redis-стейт breaker
(ADR-3.3, T-CONNECTOR-06).

## 3. Функциональные требования

FR-1. Декоратор оборачивает вызовы провайдера в порядке: bulkhead -> retry -> circuit
breaker -> пер-попыточный таймаут -> адаптер. `VerifyWebhook` и `Capabilities`
пробрасываются напрямую (локальные операции без сети; подпись проверяется по сырому телу).

FR-2. Таймауты попыток по бюджету `CBL-003`: `CreateInvoice` 2 с, `GetPayment` 1 с,
`CreatePayout` 2 с, `GetPayout` 1 с. `Capabilities` не имеет контекста в порту и
пробрасывается напрямую (200 мс из `CBL-003` - бюджет адаптерного `GetCapabilities`
задачи 3.2). Бюджет честно распределен так: при таймаутных сбоях в дедлайн RPC
гарантированно укладываются две полные попытки, третья выполняется по остатку бюджета
вызывающего; при исчерпании дедлайна возвращается ошибка контекста
(`context.DeadlineExceeded`), которую транспорт маппит в `UNAVAILABLE`. Таймаут попытки -
временная ошибка; общий контекст вызывающего уважается всегда (отмена и дедлайн
прекращают ретраи).

FR-3. Ретраи: только для временных ошибок (`domain.ErrTemporary`, таймаут попытки,
сетевые сбои адаптера) и только для идемпотентных вызовов (мутирующие методы несут
`idempotency_key`; пустой ключ - fail-fast `ErrInvalidGatewayRequest` без обращения к
провайдеру, чтобы повтор не создал второй счет или выплату). Постоянные ошибки
(`domain.ErrRejected`, валидация) и открытый breaker не повторяются; неизвестные ошибки
считаются постоянными (fail-fast). Параметры: до 3 попыток, база 100 мс, множитель 1.5
(зафиксирован явно), потолок 1 с, jitter 50% (`cenkalti/backoff/v4`, `MaxElapsedTime=0`,
остановка по числу попыток). Исчерпание попыток - `ErrProviderUnavailable` с сохранением
причины.

FR-4. Circuit breaker (`sony/gobreaker`, in-process, на провайдера): открывается после 5
подряд неудач провайдера, время размыкания 30 с, в half-open допускается 1 пробный вызов;
в открытом состоянии вызовы отклоняются мгновенно (`ErrProviderUnavailable`) без обращения
к провайдеру; успех в half-open закрывает breaker, неудачная проба снова размыкает.
Неудачей провайдера считаются только временные сбои и таймауты попыток; бизнес-отказы
(`ErrRejected`, `ErrInvalidRoute`, `ErrUnsupportedNetwork`, `ErrInvalidGatewayRequest`,
`ErrUnknownState`) и отмена вызывающего не учитываются - поток отвергнутых адресов не
должен размыкать breaker для всех мерчантов; неизвестные ошибки считаются неудачей
(консервативно). Переходы состояния логируются (warn).

FR-5. Bulkhead: не более 32 одновременных логических вызовов провайдера (слот держится на
все попытки одной операции); при исчерпании - мгновенный отказ `ErrProviderOverloaded` без
ожидания. Слот освобождается всегда, включая панику адаптера (паника пробрасывается
наружу, контракт порта не перехватывает ее).

FR-6. Классификация ошибок: адаптеры (3.2/3.7) обязаны оборачивать временные сбои
`domain.ErrTemporary`, отказы бизнес-уровня - `domain.ErrRejected`; неизвестные ошибки в
декораторе считаются постоянными и не ретраятся. Адаптеры обязаны санитизировать текст
ошибок (без URL с ключами, заголовков и тел ответов провайдера): ошибки попадают в логи
ретраев. Observation: каждый ретрай логируется (zap warn: операция, попытка, задержка,
причина), переходы breaker - warn.

FR-7. Конфигурация: значения по умолчанию разумны без env; переопределения через
`CONNECTOR_RETRY_MAX_ATTEMPTS`, `CONNECTOR_RETRY_BASE_DELAY`, `CONNECTOR_RETRY_MAX_DELAY`,
`CONNECTOR_BREAKER_FAILURE_THRESHOLD`, `CONNECTOR_BREAKER_TIMEOUT`,
`CONNECTOR_BREAKER_HALF_OPEN_REQUESTS`, `CONNECTOR_BULKHEAD_MAX_CONCURRENT`,
`CONNECTOR_PROVIDER_ATTEMPT_TIMEOUT` (перекрывает таймауты FR-2; выше бюджета RPC
ответственность оператора). Несколько уровней защиты: некорректные значения игнорируются,
после парсинга конфигурация нормализуется - нули заменяются значениями по умолчанию,
значения ограничиваются сверху (`MaxAttempts` 10, задержка 30 с, порог breaker 100,
таймаут breaker 1 ч, half-open 16, bulkhead 1024, таймаут попытки 30 с; база не выше
потолка задержки), чтобы «валидные, но безумные» env не отключали защиту.

## 4. Контракты

Внешние контракты не меняются: декоратор реализует существующий порт
`domain.PaymentGateway` (CF-1), дедлайны RPC - `CBL-003` (CreateInvoice 5 с,
GetGatewayPayment 3 с, GetCapabilities 200 мс).

Контракт классификации для адаптеров (3.2/3.7):

| Ответ провайдера | Классификация | Поведение декоратора |
| :-- | :-- | :-- |
| сетевой сбой, таймаут, 408/429, 5xx | `domain.ErrTemporary` (`%w`, причина сохраняется) | повтор по FR-3 |
| бизнес-отказ 4xx (адрес отклонен, лимит) | `domain.ErrRejected` | fail-fast, breaker не размыкается |
| 401/403 и прочие неизвестные | без оборачивания | fail-fast, breaker считает неудачей |

Маппинг в gRPC (транспорт 3.4): `ErrProviderUnavailable` -> `UNAVAILABLE`,
`ErrProviderOverloaded` -> `RESOURCE_EXHAUSTED`, `ErrRejected` -> `FAILED_PRECONDITION`,
`ErrTemporary` (после исчерпания попыток уже обернута в `ErrProviderUnavailable`) ->
`UNAVAILABLE`, дедлайн вызывающего -> `DEADLINE_EXCEEDED`.

## 5. Модель данных и миграции

Не применимо: схема не меняется. Состояние breaker - in-process (ADR-3.3);
Redis-ключ `cb:{provider}` из `CBL-003` (раздел 7) не используется до появления
требования общего состояния (T-CONNECTOR-06, KI-connector-07).

## 6. Конечные автоматы

Circuit breaker: closed -> open (порог подряд идущих неудач) -> half-open (по таймауту)
-> closed (успешная проба) | open (неудачная проба). Состояния - стандартные gobreaker,
переходы не расширяются.

## 7. Edge cases

Успех с первой попытки; временная ошибка затем успех; постоянная ошибка без ретраев;
неизвестная ошибка fail-fast; все попытки временные (исчерпание -> `ErrProviderUnavailable`
с причиной); таймаут попытки ретраится; отмена и дедлайн вызывающего прекращают ретраи;
breaker открывается и отклоняет без вызова провайдера; бизнес-отказы и отмена не
размыкают breaker; half-open выздоравливает; half-open снова падает (breaker снова open);
bulkhead полон (второй вызов отклоняется мгновенно); слот bulkhead освобождается после
ошибок и паники адаптера; пустой `idempotency_key` у мутирующих вызовов - fail-fast без
обращения к провайдеру; пустой provider name; jitter нулевой (тесты) и полный; нулевой и
экстремальный конфиг (клэмпы FR-7).

## 8. Нефункциональные требования

Оверхед декоратора на успешный вызов - единицы микросекунд (один select и обертки);
памяти - O(1). Детерминированные unit-тесты: часы backoff инжектируются, breaker-тесты
используют короткие таймауты; sleep в тестах ограничен десятками миллисекунд. Покрытие
пакета не ниже 85% (критичный путь денежного контура).

## 11. Открытые вопросы и решения

- ADR-3.3: circuit breaker in-process (gobreaker на провайдера), общий Redis-стейт
  `cb:{provider}` не реализуется до появления требования мультиинстансной согласованности
  (T-CONNECTOR-06, KI-connector-07): ключ зарезервирован и не является источником истины;
  цена in-process - при I репликах фактический порог размыкания растет пропорционально и
  half-open-пробы множатся, что принимается до задачи консолидации.
- ADR: неудачей breaker считаются только временные сбои и таймауты попыток; бизнес-отказы
  и отмена вызывающего не размыкают breaker (иначе поток отвергнутых адресов или багов
  вызывающего блокирует здорового провайдера для всех мерчантов); неизвестные ошибки -
  консервативно неудача.
- ADR: ретраи только для классифицированных временных ошибок; пустой `idempotency_key`
  у мутирующих вызовов - fail-fast: декоратор - последняя точка контроля перед повтором,
  который иначе мог бы создать второй счет или двойную выплату.
- ADR: bulkhead держит слот на всю операцию (включая паузы backoff): ограничение на
  провайдера важнее пропускной способности одиночного запроса; отказ мгновенный, без
  очереди ожидания (иначе таймауты вызывающих копятся). Паника адаптера пробрасывается
  наружу, слот освобождается через defer.
- ADR: конфигурация нормализуется и ограничивается сверху (FR-7): «валидные, но безумные»
  env не должны отключать защиту провайдера.
- Открытый вопрос: адаптерный e2e с mock-gateway (`fail_next`, `latency_ms` из 3.6) и
  контрактные тесты - задачи 3.2 и 3.7 (блокированы KI-01).
- Открытый вопрос: один экземпляр `Resilient` на провайдера создается роутером 3.4 при
  построении таблицы маршрутов (зависимость 3.4 от 3.3 зафиксирована в `CBL-004`).
